## 一、8 個失敗分成兩個完全不同的原因

### 原因 A：隨身碟的 FAT32 目錄項損壞（5 件）— 非應用程式問題

```
[failed] E:\Anime OST\Gundam\MAD機動戦士Zガンダム水の星へ愛をこめて森口博子K高画質高音質OP.mp3
      -> scan: no audio stream
[failed] E:\EasterEgg\我的出租屋里真的有很多蟑螂，但我认识的粥批真的没有几个.mp3
      -> scan: no audio stream
[failed] E:\JPOP\LSC\ラブリーサマーちゃん+-+あなたは煙草　私はシャボン.mp3
      -> scan: no audio stream
[failed] E:\JPOP\ZUTOMAYO\ずっと真夜中でいいのにハゼ馳せる果てるまでMV.mp3
      -> scan: no audio stream
[failed] E:\Miku\初音ミク このふざけた素晴らしき世界は僕の為にある n.k.mp3
      -> scan: no audio stream
```

已證實的機制（實測，非推測）：這 5 筆是**目錄項損壞**的幽靈檔案。
- `readdirSync` 列得出它們，`dirent.isFile()` 也回 true；
- 但 `lstatSync`、`statSync`、`openSync` 一律失敗，錯誤是 `errno -4094 / UNKNOWN: unknown error`；
- 用 ffprobe 直接讀其中任何一個的**原始路徑**都失敗，而同一支隨身碟上其他 200 多個檔案全部正常。

`no audio stream` 是**掃描器給的假訊息**：`probe()` 在檔案開不了時仍寫出 `{\n\n}` 這種可解析的空 JSON，於是 `streams` 為空，`library.ts` 把它判成「沒有音訊串流」。

**處置**：已修（見下方缺陷 1）。修正後這 5 筆會被列成「無法讀取／裝置損壞」，不再誤導成音訊問題。

### 原因 B：改名時撞上損壞的目錄項（3 件）— 需要可行動的訊息

```
[failed] E:\JPOP\ZUTOMAYO\05 脳裏上のクラッカー.mp3
      -> UNKNOWN: unknown error, rename '...\ずっと真夜中でいいのに。 - 脳裏上のクラッカー.aus-tmp-njd6dz.mp3'
              -> '...\ずっと真夜中でいいのに。 - 脳裏上のクラッカー.mp3'
[failed] E:\JPOP\ZUTOMAYO\消えてしまいそうです.mp3
      -> UNKNOWN: unknown error, rename '...\ずっと真夜中でいいのに。 - 消えてしまいそうです.aus-tmp-kbwnnx.mp3'
              -> '...\ずっと真夜中でいいのに。 - 消えてしまいそうです.mp3'
[failed] E:\waitting list\コンテンポラリのダンス.flac
      -> UNKNOWN: unknown error, rename '...\篠澤 広 (CV. 川村玲奈) - コンテンポラリのダンス.aus-tmp-fhi6st.mp3'
              -> '...\篠澤 広 (CV. 川村玲奈) - コンテンポラリのダンス.mp3'
```

實測根因：**目標檔名也被損壞的目錄項佔住**。
- `readdirSync` **不**列出目標名；
- 但 `statSync(target)` 不是丟 `ENOENT`，而是丟 `UNKNOWN: unknown error` —— 一個正常的「不存在」永遠不會這樣回答。

所以 `renameSync` 失敗，而失敗訊息只留下原始 errno 文字，使用者無法知道要做什麼。

目前行為是安全的：`discardStaged()` 會刪掉暫存檔，**原檔一個位元組都沒動**，也沒有留下 `.aus-tmp-` 垃圾（實測整個 `E:\` 遞迴 0 筆殘留）。

**處置**：交由 task-7 —— 改成判定「存在但不可用」並給出「目標檔名在這台裝置上損毀…請用磁碟檢查工具修復這個資料夾，或先在電腦上轉換後再複製回來」這類可行動訊息，同時保留原始錯誤文字。

## 二、應用層的三個真缺陷

### 缺陷 1：掃描器把「開不了檔」錯報成「沒有音訊串流」

- 成因：`src/core/probe.ts` 在 ffprobe 失敗時仍回傳可解析的空 JSON；`src/core/library.ts` 只憑 `!info.audio` 就下 `no audio stream` 的結論。
- 影響：使用者被引導去懷疑自己的檔案編碼，而真正的問題是裝置損壞。
- 狀態：**已修**（掃描層後續併入 task-6 的敘述調整）。

### 缺陷 2：暫存檔被當成音樂檔掃進來，產生 `(2)` 重複檔

真實報告中同一首歌出現兩列：

```
FROM E:\Anime OST\Attack On Titan\...FullName of Loveby cinema staff.aus-tmp-u9nvkk.mp3
TO   E:\Anime OST\Attack On Titan\...FullName of Loveby cinema staff.mp3
FROM E:\Anime OST\Attack On Titan\...FullName of Loveby cinema staff.mp3
TO   E:\Anime OST\Attack On Titan\...FullName of Loveby cinema staff (2).mp3
```

- 成因：`runBatch` 的暫存檔命名是 `<原名>.aus-tmp-<6字><副檔名>`，而 `walk()` 只用 `extname()` 比對副檔名 —— `.aus-tmp-u9nvkk.mp3` 的 extname 是 `.mp3`，所以上次崩潰留下的暫存檔被當成音樂檔，轉換後又就地改名，與真檔撞名而產生 `(2)`。
- 影響：**在隨身碟上製造重複檔並浪費容量**，且使用者不會知道那是怎麼來的。
- 狀態：交由 **task-6**（掃描排除 + 清除殘留暫存檔）。

### 缺陷 3：就地覆寫會替使用者改檔名（政策問題，需使用者決定）

199 項中有 **123 項**的輸出路徑與來源路徑不同，例如：

```
E:\Anime OST\Bocchi the rock\002-ひとりぼっち東京.mp3  ->  E:\Anime OST\Bocchi the rock\結束バンド - ひとりぼっち東京.mp3
E:\Anime OST\Attack On Titan\So Ist Es Immer - Sawano Hiroyuki.mp3
                                                    ->  E:\Anime OST\Attack On Titan\Sawano Hiroyuki - So Ist Es Immer (2).mp3
```

改名是 `{artist} - {title}` 命名樣式造成的。它有時是好事（把 `002-` 這種編號清掉），但它沒被要求、會與損壞目錄項相撞而整列失敗，而且失敗時使用者只看到一個 errno。

- **已決定（2026-10-16）**：使用者選擇「**保留原檔名**」。就地覆寫的預設行為改為**絕不改名**。
- 狀態：交由 **task-7** 實作（`overwrite: true` 且未指定 `preserveNames` 時預設為 `true`；`outputPath` 必須等於來源路徑），**task-8** 的 UI 同時帶上 `preserveNames: true`。明確傳 `preserveNames: false` 時仍可用 `{artist} - {title}` 整理檔名。

## 三、裝置健康建議

`E:\` 的目錄結構已有至少 6 筆損壞的目錄項（5 筆讀不到 + 至少 1 筆佔住改名目標）。這不是應用程式能修的。

建議（**使用者已表示要自行處理，本報告不代替他做決定**）：

1. **先備份能讀的檔案**（191 個已在這次批次中就地轉換並複驗通過，但備份仍優先於任何修復）。
2. 對 `E:` 執行 `chkdsk E: /f`（會嘗試修復目錄項）。若無效，**格式化重建** FAT32，或改用好一點的檔案系統（exFAT）。
3. 重新格式化後，把備份複製回去，再用本程式重跑一次。

在裝置修好之前，這 8 筆會持續失敗，而**其餘檔案都能正常處理**（191/199 已證明）。

## 四、缺陷 2 留下的 `(2)` 重複檔：實測清點

缺陷 2 已經在使用者的隨身碟上留下 8 個 `(2)` 檔，合計 **76,673,344 bytes（76.7 MB）**。處置前必須知道它們是不是真的重複，所以逐一與同名的原檔做了 **SHA-256 與時長比對**（不是只看檔名或大小）：

| 檔案 | 原檔 | `(2)` | 判定 |
|---|---|---|---|
| `Attack on Titan - Ending 5 FullName of Loveby cinema staff` | **不存在** | 10,589,047 B / 264.490 s | **只剩 `(2)`，原檔名消失** |
| `Sawano Hiroyuki - So Ist Es Immer` | 8,914,292 B / 222.786 s | 11,590,276 B / 289.680 s | **不同錄音**（差 66.9 s） |
| `結束バンド - カラカラ` | 10,743,374 B / 268.368 s | 8,652,533 B / 216.093 s | **不同錄音**（差 52.3 s） |
| `結束バンド - あのバンド` | 8,665,064 B / 216.408 s | 8,665,064 B / 216.408 s | 同長度，位元組不同 |
| `結束バンド - 小さな海` | 9,072,578 B / 226.608 s | 9,072,578 B / 226.608 s | 同長度，位元組不同 |
| `結束バンド - ギターと孤独と蒼い惑星` | 9,278,458 B / 231.744 s | 9,278,458 B / 231.744 s | 同長度，位元組不同 |
| `結束バンド - ひみつ基地` | 9,413,209 B / 235.104 s | 9,413,209 B / 235.104 s | 同長度，位元組不同 |
| `結束バンド - ひとりぼっち東京` | 9,412,179 B / 235.080 s | 9,412,179 B / 235.080 s | 同長度，位元組不同 |

統計：**位元組完全相同 0 個**、同長度但位元組不同 5 個、不同錄音 2 個、原檔消失 1 個。

結論與提醒：

1. **不可以按檔名批次刪除這 8 個檔案。** 有兩個 `(2)` 的時長與它的原檔差了 50–67 秒，代表它們**不是同一段錄音**；其中至少有一個是原本不該出現在那個資料夾的曲子。刪掉任何一個都可能永久失去一首歌。
2. **`Attack on Titan - Ending 5 ... (2).mp3` 是那個名字僅存的一份**。原檔名已經不存在，所以這個檔案**不能刪**（至少要先改名或移到安全位置）。缺陷 2 的「先轉換暫存檔、再轉換真檔、最後刪掉真檔」序列，就是它消失的原因。
3. 5 個「同長度、位元組不同」的檔案最有可能是同一段音訊重新編碼後的產物（編碼器相同、長度相同、位元組不同），但**這只是從資料推出的假設，沒有聽測驗證**，所以不能當成刪除依據。
4. 建議的處置順序：**先整支隨身碟備份**（見第三節），再用耳朵或音訊比對工具逐一確認這 8 組，最後才刪除確認多餘的 `(2)`。這 8 個檔在裝置修好與人工確認之前**不要動**。

根因（缺陷 2）已由 **task-6** 修掉：`walk()` 現在會在任何 `extname()` 判斷之前跳過檔名含 `.aus-tmp-` 的項目（`src/core/library.ts:118`），所以殘留暫存檔不會再被當成音樂檔。**task-10** 另外把 `sweepStaleStaging()` 接進真實批次流程，讓下次執行前就清掉殘留。`(2)` 後綴本身的來源（改名撞名）由 **task-7** 的 `preserveNames` 預設值關掉——就地覆寫不再改名，也就不會再產生 `(2)`。
