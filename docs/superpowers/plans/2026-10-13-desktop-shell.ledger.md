## Post-acceptance fixes

The desktop build shipped, and then failed on the first real double-click. Recorded here because
every test that existed at the time was green — the failure was invisible to all of them.

| # | Symptom | Root cause | Fix | Evidence |
|---|---|---|---|---|
| F1 | Double-clicking `AudioUsbStudio.exe` reported `the engine exited with code 1 (attempt 5 of 5)` with `(no engine log was written)`, and no window ever appeared. | (a) `tools/launcher.cjs` had exactly one place to unpack its assets (`%TEMP%\aus-app-*`) and called `process.exit(1)` when Windows refused the `mkdir`; (b) the shell swallowed its failure to create `engine.log` in a bare `catch { }`; (c) `LogTail()` never read the log the launcher writes beside the engine executable, which held the real reason; (d) the retry loop spent five attempts on a failure no retry could change; (e) the tests only ever launched `release\AudioUsbStudio.exe`. | Unpacking tries four locations in turn; the shell records why its log is unavailable, drains the engine output pumps before reporting, reads `AudioUsbStudio-error.log`, and stops retrying as soon as that file exists; `resolveScratchRoot()` degrades the same way. | With a hostile `TEMP` (`TEMP=<repo>\package.json\sub`, so `mkdir` fails with `ENOTDIR`), `doctor` exits 0 and reports `scratch: ...\engine\.aus-scratch`, and no unpacker log is written — verified for both `release\` and the shipped `engine\`. |
| F2 | After F1, double-clicking still failed: `System.UnauthorizedAccessException: Access to the path 'C:\Users\TINGOD\AppData\Local\AudioUsbStudio\WebView2' is denied`, thrown from `MainForm.EnsureWebViewAsync` and caught by `StartEngineAsync`. | A second, independent `%LOCALAPPDATA%` path was refused — this time the WebView2 profile. The shell still assumed that directory was writable (F1 taught the unpacker not to, but the shell kept its own assumption), and `Program.ReportFatal` wrote its crash log there too, so the two components that must report failures were the two most likely to fail. | `ShellPaths` gains `DataDirCandidates` / `TryResolveDataDir`, which probe each candidate with a real write; `MainForm` resolves one directory up front and uses it for both the engine log and the WebView2 profile; `EnsureWebViewAsync` reports which folder was refused instead of letting a raw stack trace be the message; `Program.ReportFatal` resolves the same way. | `66/66 passed`. A search confirms no code is left picking a single user-profile path: the only `GetFolderPath` calls remaining are the candidate list itself. |

## Known warnings

`MSB3277: WindowsBase 4.0.0.0 vs 5.0.0.0` on every build. Comes from the WebView2 package's
`buildTransitive` targets pulling `Microsoft.Web.WebView2.Wpf.dll` even though only the
WinForms surface is used. Harmless — the WPF assembly is not loaded — but it is noise that
should be silenced once Task 10 actually constructs a `WebView2` control.
